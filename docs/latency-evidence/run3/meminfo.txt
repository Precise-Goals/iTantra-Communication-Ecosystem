Honest read: the STT session object cache is verifiably bounded to 2 entries at all times (every
tap beyond the 2nd distinct language logs exactly one "Evicted STT session" line; grep count in
sender_logcat.txt confirms this). But TOTAL PSS is NOT flat across repeated switches -- it grew by
+220MB then +67MB across two rounds of two-taps-each, even though the object count stayed constant.
Most likely cause: OrtSession.close() releases the Kotlin object and the model's file mapping, but
onnxruntime's internal memory arena does not necessarily munmap/return freed native allocations to
the OS immediately -- so switching between many *different* models (each with its own arena) can
still show elevated PSS from allocator fragmentation, even though no single model is duplicated.
The growth is decelerating (220 -> 67 MB across equal-sized two-tap intervals), consistent with the
allocator starting to reuse already-freed blocks rather than an unbounded per-tap leak, but it is
real and should not be reported as "RAM stays flat."
