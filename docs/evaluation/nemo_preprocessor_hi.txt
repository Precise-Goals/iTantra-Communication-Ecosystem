=== Behavior confirmed from FilterbankFeatures source (not a constructor field, but real,
    checked behavior — inspect.getsource on the installed package) ===

1. Window: `window_fn(self.win_length, periodic=False)` — a SYMMETRIC Hann window
   (denominator N-1), not torch.hann_window's own periodic default (denominator N). The working
   tree had this backwards (T27 "periodic Hann window" was a wrong assumption; reverted by T23).

2. Dither: applied only `if self.training` — disabled at inference/eval. No dither needed in the
   Kotlin feature extractor, and none was added.

3. STFT call: `torch.stft(x, n_fft=512, hop_length=160, win_length=400, center=True,
   window=<the 400-sample window above>, return_complex=True, pad_mode="constant")`.
   center=True (since exact_pad defaults False) pads the signal by n_fft//2=256 zeros each side;
   pad_mode="constant" means that padding — and any part of a centered analysis window that
   falls outside the real audio — is zero, not reflected. Net effect: frame t is centered at
   original sample t*hop_length, spanning the 400-sample window either side, with out-of-range
   samples treated as zero. Physical frame count = 1 + floor(audio_len / hop_length).

4. get_seq_len(): floor(audio_len / hop_length) — exactly one less than the physical frame count
   above. forward() masks (zero-fills) every frame at or beyond this "valid" length, and
   normalize_batch's per_feature mean/std are computed only over the valid frames. Net effect for
   a single, unpadded utterance: the very last physical frame is excluded from normalization
   statistics and is hard-zeroed in the output, for any input length.

5. normalize_batch(..., normalize_type="per_feature"): unbiased variance
   (`sum((x-mean)**2) / (N - 1)`, N = valid frame count), epsilon added to std is
   CONSTANT = 1e-5 (same value already used in the working tree).

6. Mel filterbank: `librosa.filters.mel(sr=16000, n_fft=512, n_mels=80, fmin=0, fmax=8000,
   norm='slaney')` — called WITHOUT `htk=True`, so librosa's Slaney mel *scale* applies
   (hz_to_mel/mel_to_hz below), which is a different formula from the HTK scale
   (2595*log10(1+f/700)) the working tree had. This is separate from T25's "Slaney
   normalization" (the 2/(upper-lower) filter-area scaling, which was already correct) — the
   scale formula itself had never been checked against the real config before now.

   librosa hz_to_mel / mel_to_hz (htk=False), from the installed librosa's own source:
     f_sp = 200/3 ; min_log_hz = 1000 ; min_log_mel = min_log_hz / f_sp ; logstep = ln(6.4)/27
     hz_to_mel(f)  = f / f_sp                          if f < min_log_hz
                   = min_log_mel + ln(f/min_log_hz)/logstep   otherwise
     mel_to_hz(m)  = f_sp * m                           if m < min_log_mel
                   = min_log_hz * exp(logstep*(m - min_log_mel))  otherwise
